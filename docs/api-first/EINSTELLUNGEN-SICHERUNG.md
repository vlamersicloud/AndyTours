# API-Einstellungen und Sicherung – Design (Quelle: bereitgestellter Kontext)

**Bestand:** `Sicherungseinstellungen` liegen je Datenordner in SQLite: Standardintervall 3 Starts, Aufbewahrung 10, Ordner `Sicherungen`, Intervall/Aufbewahrung 1–99. `StartsSeitSicherung` ist ein separater Zähler: Start zählt sofort; bei fälliger erfolgreicher Sicherung wird er 0, bei Fehler bleibt er stehen. Ein Datenordnerwechsel wechselt damit auch Einstellungen und Zähler. (Core `Sicherungseinstellungen.cs`, Daten `FuehreStartsicherungDurch.cs`.) Lokale UI-Präferenzen (Fenster/Layout) sind davon zu trennen; sie dürfen nicht den backendweiten Sicherungszustand überschreiben.

**Erster kleinster Schnitt:** typisierter versionierter Read/Write-Vertrag ausschließlich für Intervall und Höchstzahl, mit serverseitigen Defaults und Bereichsprüfung 1–99. Version/CAS verhindert verlorene parallele Änderungen. Der Startzähler bleibt serververwaltet und unabhängig von der Richtlinienversion; er darf lesbar an die UI ausgegeben, aber weder im Request gesetzt noch durch Richtlinienänderungen verändert werden. Keine Dateipfade in Request/Response. Einen vorhandenen konfigurierten Sicherungsordner erhalten; nur wenn keiner gesetzt ist, gilt der Legacy-Standardordner. Keine stillschweigende Rücksetzung.

**Folgestufe – Sicherungen:** opaque IDs statt Dateipfaden; serverseitige Auflistung/Download, strikte Namens-/Inhaltsprüfung, temporäre Datei und sichere Bereinigung. Legacy-Code erstellt eine konsistente SQLite-Kopie per Online-Backup und atomarem Temp-Umbenennen, listet nur streng benannte `.db`-Dateien und begrenzt Retention (`ErstelleSicherung.cs`, `ErmittleSicherungen.cs`). Das belegt keine vollständige Archivierung von Anhängen. Ziel ist ein vollständiges versioniertes Archiv aus Datenbank, FIT-Dateien und Anhängen; bestehende SQLite-only-Dateien müssen mit explizitem Hinweis auf ihren begrenzten Umfang behandelt werden.

**Restore:** nur explizit im UI mit Vorschau und erneuter Bestätigung; zuerst automatische Sicherung des aktuellen Bestands. Erfordert datasetweite Schreibsperre/Exklusivität über alle Clients und anschließende Versions-/Cacheinvalidierung. Keine beliebigen Pfade oder unkoordinierte `File.Move`-Ersetzung einer aktiven Backenddatenbank. Legacy-Implementierung prüft, sichert, bereitet temp vor und ersetzt lokal (`SpieleSicherungZurueck.cs`); das beweist keine sichere verteilte Restore-Parität.

Offen: Identität/Versionierung der Datensätze, Schreibsperren und Client-Invalidierung, Anhänge/Manifest, Downloadgröße/Retention sowie wer den Sicherungsordner administriert. Der erste Vertragsschnitt ist ausschließlich vorbereitet; ein Endpoint oder eine Integration ist nicht implementiert. Kein Teil der API-Migration wird hier als umgesetzt behauptet.
